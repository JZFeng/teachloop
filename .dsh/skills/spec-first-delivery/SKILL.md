# Spec-First Delivery

一句话：**先把不确定的东西问清楚、写成可验收的文档、画成能点的原型，让用户逐份确认；确认前一行业务代码都不写。**

## 何时使用

- 用户要做一个较大的功能或系统（不是改个 bug、加个字段）。
- 用户说「先梳理需求」「按规范文档来」「先 plan 再动手」「先画原型」。
- 用户已经生气：「我还没说完呢，你怎么就咣咣开始写了」——立刻停下，把已完成的东西回退到文档阶段。

**不适用**：明确的单点修复、用户已给出完整规格且只要执行的任务。

## 七阶段与退出条件

每个阶段有**唯一产出物**和**唯一退出条件**。退出条件没满足，不许进下一阶段。

| 阶段 | 产出物 | 退出条件 |
| :--- | :--- | :--- |
| 1. Research | 对比 5–10 个同类系统，写进 `.docs/research/` | 能说清别人的做法和取舍，而不是自己想 |
| 2. Constitution | 不可协商的约束（隐私、可观测、i18n、模块边界…） | 每条都能在后续文档里对应到具体条款 |
| 3. Spec | 用户故事 + 可验收的验收标准 + 功能需求 | 每条验收标准都能被第三方判定通过/不通过 |
| 4. Mock | 可点击的界面原型（单文件 HTML 最快） | 用户能自己点开、走完主流程、指出哪里不对 |
| 5. Plan | 架构、数据模型、模块与端口、迁移路径、测试策略 | **下方 6 条清单全部打勾** |
| 6. Tasks | 按依赖排序的任务，每个带自己的验收 | 无重复编号，无孤儿任务，能反查覆盖 |
| 7. Implement | 代码 | **用户明确说「开始实现」** |

### Spec ⇄ Mock 是一个循环，不是两段直线

```
Spec ──→ Mock ──→ 发现缺口 ──→ 回写 Spec ──→ 改 Mock
```

**Mock 是需求检验工具，不是装饰。** 真实教训：一个项目里 Mock 是最后才画的，画的时候一口气冒出 7 个用户故事、40 条验收标准——教师首页该不该跨班聚合、批改总览和复核工作台是不是两个页面、考试页要不要左右分栏，全是画到那一步才定下来的。如果 Mock 排在 Plan 之后，Plan 里所有基于旧需求的判断都要重做。

推论：**Mock 必须在 Plan 之前**。反过来，Plan 定稿后仍然可以改视觉细节（配色、间距），但那时改的是方案不是需求。

## Plan 的 review 清单（6 条）

这是本项目付过学费的地方：plan 我只问了自己「每条验收标准能不能实现」，从来没问过「这张表会不会被两个模块写」，于是 plan 被判定通过、tasks 也拆完了，用户提出模块化时才回头重做——九个模块、宪法加了一条、三个任务全部重写。

一次性看完，逐条打勾，不分遍：

**完整性**

1. spec 的每一条验收标准，都能在 plan 里指出由哪个表、哪个流程承接吗？
2. 每个实体的表、关键字段、索引、状态迁移都写全了吗？
3. 每条外部依赖（AI 模型、对象存储、微信、队列）都写了失败与重试路径吗？

**结构**

4. 模块依赖方向有环吗？跨模块调用是否只走端口？
5. 每张表是不是只有一个属主？有没有跨模块 JOIN？
6. 拆服务路径写得出来吗（哪几个进程、先拆谁、数据怎么切）？

**任一条打不上勾 → plan 不定稿 → 不拆 tasks。**

1–3 回答"能不能做出来"，4–6 回答"做出来会不会烂"。两类要分开问，因为问 A 的时候想不到 B。

## Review 是每份产出物的闸门

| 产出物 | 这次 review 要回答的问题 |
| :--- | :--- |
| Research | 别人的取舍讲清楚了吗？还是只有"XX 也用这个"？ |
| Constitution | 每条约束都能对应到后续某个具体条款吗？ |
| Spec | 每条验收标准第三方能不能判定通过/不通过？有没有把实现方式写进需求？ |
| Mock | 主流程点得通吗？状态（空白/有数据/出错）都有吗？数据是真的吗？ |
| Plan | 上面那 6 条清单 |
| Tasks | 依赖顺序对吗？每个任务自己能验收吗？ |

用户不确认，就不往下一阶段走。**不要一次给用户看五份文档**——他只会看第一份。

## 提问纪律

- 需要用户拍板的事，**用 question 工具**（`ask_user_question` 单选/多选，复杂场景用 `ask_survey`），不要写成正文里的一句话问句。真实教训：用户说过「我还是通过 question 方式讨论吧，我不擅长在答案里找问题」。
- 一次 1–3 个问题。每个选项必须是**立场不同**的，不能是「A. 好 / B. 也行」。
- 选项里写清代价，不只是好处。用户选的是取舍，不是菜单。
- 用户选完要**回读一句**：「你选了 X 而不是 Y，因为 Z，所以我接下来……」——确认没理解错，也让他知道自己的选择被记住。

## 红线（都是真实踩过的）

1. **规范未确认就写业务代码** —— 最严重。可以做调研、跑一次性验证脚本、搭原型（用完删），但不能落业务实现。
2. **Mock 排在 Plan 之后** —— 需求缺口暴露得太晚，Plan 和 Tasks 全部返工。
3. **Plan 只审"能不能实现"，不审"结构会不会烂"** —— 上面那 6 条里的 4–6 就是这么漏掉的。
4. **文档之间数字不一致** —— 题型从 75 改到 76 又到 77，客观/主观从 125+25 改成 120+30，分数一处 136 一处 138。用户一眼就能看出来，信任直接崩。
5. **原型数据与真实数据不符** —— mockup 里分值全是我编的，用户问「这是按我给你的试卷 mock 的吗」才发现全错。用真实数据渲染，别手抄。
6. **把一个概念的错误建模固化下去** —— 曾把「部分类型」和「作答形式」绑死（部分叫完形就渲染下拉），实际作答形式是**每题自己的属性**。
7. **同一概念两套命名** —— `input_type` 与 `question_type` 并存，渲染层就分不出单选和多选。定名后全局替换，不留旧名。
8. **文档腐化** —— 宪法里还写着 Python/FastAPI/Celery，而技术栈早已是 Java。**改架构必须回改宪法**，否则实现时每条都是「违宪」。
9. **没验证就说已验证** —— 起不了浏览器却只说「结构校验通过」。正确写法：「仅做了结构校验，视觉效果未确认，需要你打开看」。
10. **把待定问题埋在正文** —— 用户不会去文章里找问号。

## 原型怎么画（省钱版）

- **一个 HTML 文件**，内联 CSS + 原生 JS，无构建、无依赖，双击就能开。用户要发给别人看也不会坏。
- 顶部放一个 `go('screenName')` 路由 + 左侧导航，所有界面塞在这一个文件里。
- **数据用真实数据渲染**：从用户的真卷/真表抽成 JSON，页面由数据生成，不要手抄进 HTML。
- 主题用 CSS 变量，两三套就够（默认亮色 + 一键切换），不要写死颜色。
- 每屏都必须自制状态：空白态、有数据态、出错态。只画「有数据」的漂亮样子，用户没法判断。
- 画完**自己点一遍**：用浏览器工具逐屏截图，量 DOM 尺寸，别靠肉眼。数据显示错（人数、分值、分数合计）是最高频的 bug。

## 收尾自检

```bash
# 四份文档计数必须互相吻合，且无重复编号
grep -c '^### US-' specs/*/spec.md
grep -c '^- \[ \] AC-' specs/*/spec.md
grep -c '^| FR-' specs/*/spec.md
grep -c '^| T[0-9]' specs/*/tasks.md

# 抽检重复编号。注意必须锚定“定义行”，否则会把正文里的交叉引用
# （如“按 AC-26.4 处理”）也算进去，报出一堆假重复。
grep -o '^- \[ \] AC-[0-9]*\.[0-9]*' specs/*/spec.md | sort | uniq -d
grep -o '^| T[0-9]*' specs/*/tasks.md | sort | uniq -d
```

每轮结束必须给用户三样东西：**改了哪些文件**、**校验结果**（真实的）、**还剩什么没定**。

## Implement 阶段开始之后

- 按 tasks 顺序做，每个任务完成即更新状态。
- 实现过程中发现的规格漏洞，**回写文档再改代码**，不要在代码里偷偷绕过。
- 每完成一个阶段跑一次测试，不要让「全绿」只出现在最后一天。
