# 决策 003 — 作业的 AI 批改改成夜间批量

日期：2026-10-22　状态：生效　相关：T092/T093（到期派发与峰谷调度）、T330–T333

## 问题

作业（`kind=ASSIGNMENT`）现在和考试共用一套调度：`due_at + grace_hours` 到点后，60 秒扫描派发，
高温时段推迟。这套口径是为考试设计的——考试统一收卷，收完就该出分。

作业不是这样：

1. **提交时间分散但成簇**：学生在下班/放学后陆续交，白天零散交几份。等「截止」没有意义，
   截止设在一周后时，早交的学生要等一周才看到反馈。
2. **反馈不是「当场要」**：AI 结果只是草稿，最终由老师进复核队列拍板。真正的时间要求是
   「老师上班前草稿准备好」。
3. **成本**：DeepSeek 夜间折扣时段是北京时间 00:30–08:30。白天全量实时批等于按原价跑；
   现有 `peak-aware` 那套「工作日 9–12 / 14–18 不派发」是在用轮询+推迟绕这个成本问题，
   规则藏在代码里，老师看不见也解释不清。

## 决策

**作业改成每晚固定时刻批量跑；考试维持现状；手动派发随时可用。**

| 项 | 决定 |
| :--- | :--- |
| 适用范围 | `kind = ASSIGNMENT` 且 `status = PUBLISHED` |
| 触发 | 每晚 **02:30（Asia/Shanghai）** 扫描一次，不依赖 due 是否已过 |
| 批什么 | 所有 `grading_state = QUEUED` 的提交（学生一交就有机会当夜批，不等截止） |
| 审计语义 | 保留「一场一条 run」：首次派发建 run，之后的提交补进同一个 run |
| 兜底 | 应用启动时补跑一次（幂等）；漏跑最坏等到当晚 |
| 考试 | 不变：`due_at + grace_hours` 到点后 ~1 分钟内派发，仍受峰谷限制 |
| 手动 | 「立即派发」「让 AI 先批」「重试失败项」不受任何时间限制 |
| 配置 | `teachloop.grading.assignment-cron`（默认 `0 30 2 * * *`）、`assignment-zone`（默认 `Asia/Shanghai`）、`assignment-catch-up`（默认 `true`） |

### 为什么不是「交卷即批」

- 白天批按原价付费，而作业的时效要求并不高；
- 「随时可能跑」对老师不可预期，也不好在界面上解释；
- 需要一个全局闸门才能避免白天高峰，结果还是要回到「夜间跑」。

### 为什么考试不改

考试有时限，老师当场等结果。深夜批一份上午考的卷子，老师白天一整天看不到草稿，
反而更糟。峰谷推迟最多 4 小时，且已有「立即派发」兜底。

## 代价与对策

| 代价 | 对策 |
| :--- | :--- |
| 一晚只跑一次，02:30 正在重启就空一天 | 启动补跑 + 派发本身幂等（条件 UPDATE），可重复执行 |
| 一晚上量可能很大（几百份作文），老师早上看到「批改中」 | 进度页本来就区分 pending/running/done；补一条「今晚 02:30 自动开始」的说明，别让老师以为卡了 |
| 截止前重交会产生多份 AI 草稿 | 复核队列只显示每个学生的最新 active attempt（T331）；旧 attempt 的复核行留着，但不进队列 |
| 老师以为「发布完就自动批」 | 作业详情页与新建作业页显式写清「每晚 02:30 自动批改，急用可立即派发」 |

## 影响面

- `OfferingRepository.findDueForGrading` 加 `kind = 'EXAM'`（只服务考试）；
- 新增 `findAssignmentsWithQueued()`（作业侧「还有排队提交的场次」）；
- `OfferingGradingDispatcher.dispatchAssignments()` + `AssignmentGradingJob`（cron + 启动补跑）；
- `Ports.OfferingOwnership` 增 `activeSubmissionIds`，复核队列过滤掉被重交取代的旧 attempt；
- 前端：作业新建页 / 批改详情页各一条提示文案（zh/en）。
