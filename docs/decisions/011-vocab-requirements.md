# 决策 011 — 背单词第一期：库的结构、发词与算法边界

日期：2026-10-23　状态：生效（规格见 `specs/004-vocab/spec.md`）
上游：`specs/004-vocab/source-requirements.md`（外部需求抽取）、宪法第十四条（模块边界）

## 背景

外部需求文档（`~/Downloads/flashcard req.md`）按**个人背单词 App** 建模：每张卡片属于一个卡组，
每个用户各自一套卡组。而 TeachLoop 的主用例是：

> 老师把下一节课的生词提前发给班级 → 学生预习 → 这些词进入学生的**总词汇库**（缺省库）。

两者放在一起会产生一个具体问题：**每课一个卡组 → 一学期几十个卡组 → 同一个词在多门课里重复出现**，
进度按卡组分叉，学生要背两遍、数据两份。用户在 2026-10-23 明确提出这个担心。

## 决策一：三个对象分名，进度按 `(学生, 词条)` 唯一

| 对象 | 归属 | 增长依据 | 是否承载复习状态 |
| :--- | :--- | :--- | :--- |
| 词条 | 内容（教师词集 / 学生自建 / 导入） | 按教学内容 | **否** |
| 词集 | 教师或学生（内容资产） | 按课程/单元 | **否** |
| 学习进度 | 学生 × 词条 | 学生 × 词量 | **是，唯一一份** |

**判据**：同一个学生对同一个词，无论从几门课、几次导入进来，只有一份进度。
这条一旦破了，「爆炸」立刻发生，且无法事后合并。

## 决策二：学生侧采用模型 C —— 单库 + 少量自建卡组（保存的筛选）

三个候选与被否的理由：

| 模型 | 形态 | 结论 |
| :--- | :--- | :--- |
| A 每课一卡组 | 照源文档，课程 = 卡组 | **否**：正是爆炸来源；同一个词多份状态 |
| B 单库 + 来源关联 + 视图 | 无卡组，全部靠筛选 | 可行，但少了学生自建「易错」「托福核心」的余地 |
| **C 单库 + 允许学生自建少量卡组** | 卡组 = **保存的筛选条件**，不是容器 | **采纳**（用户 2026-10-23 选择） |

卡组不是容器带来两个后果，必须在实现与界面上体现：

1. 卡片不存在「移入/移出卡组」的操作，只有「这个视图包含哪些词」的条件。
2. 一个词可以同时出现在多个卡组视图里，但**只被排一次复习**。

## 决策三：第一期就做「教师发词给班级」

- 词集是**教师侧内容资产**，一条词集可反复布置给多个班、多次（不会因为教 6 个班变成 6 份）。
- 一次「发词」= 词集 × 班级 × 可选截止时间，**发出去时对词集内容做快照**——后续改词集不影响已发出的布置
  （与 002 的试卷快照同一套约定，避免「老师改了一个词，昨天发的作业变了」）。
- 学生领取后，词条进个人库；**删除布置不删学生已经学过的词**。
- 本期**不做**教师查看学生背诵明细（隐私见决策五）。

## 决策四：调度算法 —— 可替换策略，默认 SM-2

用户 2026-10-23 选择「不过早定，先做成可替换策略，默认 SM-2」。

- 需求层只要求：四级评分产生**可预期的不同调度结果**，且调度由可替换策略给出。
- SM-2 的参数在规格 §5 列成一张表，集中一处、可调；**调参数不算改需求**。
- FSRS 走后续迭代，不需要改表结构（进度表只存策略无关的字段：状态、到期时间、间隔、难度/易度）。

## 决策五：教师默认看不到学生背诵记录

本期只做「发词」，不做「谁背了多少、正确率多少」。理由：

- 背诵记录属于学生个人学习数据（宪法第七条隐私口径）；
- 一旦教师可见，需要先定义「预习完成」的口径、保留期与导出边界，属于独立需求。

这条要在规格里写成明确的**不做**，避免实现时被当成遗漏。

## 决策六：首期范围

采纳用户 2026-10-23 的选择：**卡片 + 卡组 + 导入 + 复习**，外加决策三的「发词给班级」。

不做：统计图表（只留「今日已复习 N 张」这类计数）、FSRS、共享词集市场、Anki 导入、音频上传、移动端。

## 2026-10-23 第二轮确认（review 规格时）

| 议题 | 结论 | 影响 |
| :--- | :--- | :--- |
| 毕业条件（4 次 / 90 天 / 180 天复查） | 保留默认值，但**必须可在 `application.yml` 改** | 规格 §5.1、FR-106 |
| 每日新卡上限（20） | 同上，走 yml | 规格 §5.1、AC-52.3 |
| 教师入口位置 | **一级导航**，不放班级页内 | 规格 AC-56.3、FR-104 |
| 词形还原 | **不做**：`run` / `running` 算两个词 | 已与 Anki 默认行为对齐（查重只看第一条字段、忽略大小写；归并靠 MorphMan 插件）；规格 A-6 |
| 教师看学生背诵进度 / 预习率 | **V1 不做**，确认不需要 | 规格 A-7、US-54、§9 |
| 发音 | 要 **TTS**，不是只存音标 | 原先的「只存音标文本」假设作废，改为 US-57 / FR-105 |

**TTS 的立场**（2026-10-23 第二次修订）：链路固定为 **缓存 → 本地引擎 → 浏览器语音**。

- 缓存：按「词条 + 音色 + 语速」的内容哈希存在**部署的存储**里——开发是本机 `./uploads`，生产是 OSS；
  不进 git、不进 jar、不入数据库 BLOB。
- 本地引擎：Piper（MIT，ONNX，模型小、合成快）或 Kokoro（Apache-2.0，82M，音质更好但更吃 CPU），
  默认用本地，不按次付费。
- 回落：本地引擎缺失或 2s 未返回，就用浏览器 SpeechSynthesis，复习流程不中断。
- `cloud`（Polly / Azure / 阿里云 / 腾讯云）保留成可选提供商，但**不是默认**；只在明确想换音色或本地资源不够时启用。
- **只朗读单词本身**，不朗读释义与例句（V1 明确不做）。

**顺带记一个架构约束**：现有的存储抽象 `StorageBackend` 在 `teachloop-sitting` 内部（模块私有），
而 vocab 按宪法第十四条只能依赖 `shared / identity / classroom`，不能直接用它。
所以「音频缓存复用哪套存储」是 plan 阶段必须回答的问题：要么把存储端口提到 `shared`（同时回改宪法第十四条），
要么 vocab 自带一个极简音频存储。这是本功能第一个会碰到宪法边界的地方。
