# 决策 022 — AI provider 故障转移（修订决策 013-A）

日期：2026-10-25　状态：**生效，待实现**　相关：决策 013（A 项被本决策取代）、D-30、US-62、FR-116–121、T482–T483

## 问题

用户 2026-10-25 提出：

> 「保护确实是个问题，我们代码应该有保护机制，比如 opencode 不能用了，可以轮询 config 里的下一个，比如 deepseek api，然后是 local。」

这与**决策 013-A「不做自动 fallback 链，v1 保持全站一个当前模型」**直接冲突。013 给的理由是：

> 同一批混用两种模型会让分数口径不一致；失败要让人知道，而不是静默换个模型继续烧钱。

所以必须先分清两件事，否则会把 013 的顾虑一起推翻：

| | 013 拒绝的东西 | 用户这次要的东西 |
| :--- | :--- | :--- |
| 触发条件 | 单份作业调用失败 | provider **整体**不可用（欠费、停机、全面 429、Key 被吊销） |
| 作用范围 | 一份一份换 | 整站切到下一个 provider |
| 用户知情 | 静默 | 审计 + 通知 + 界面显示 |
| 失败后果 | 静默烧钱、口径悄悄变 | 全班停摆等人工（1000 人规模下不可接受） |

**用户规模的变化是背景**：1000 个学生、包月套餐（opencode go）。套餐超额或拖欠时的返回通常是 401/402/403，按决策 013-B 这类**不重试**，直接 FAILED 再熔断——也就是「整班批改失败，只能人工重试」。这是本决策要解决的真实故障模式。

## 用户拍板

| 议题 | 决定 |
| :--- | :--- |
| 是否要 fallback | **要**。opencode → deepseek api → local，按配置顺序轮询 |
| 排队慢（1 小时） | **不是问题**，接受；不为此加 worker（背景：用户口径「我们小时候考试都是过好几天才有成绩」） |
| 同场作业跨模型 | 允许，但每份要能查到是由哪个 provider 判的 |
| 自动回切 | 待实现前确认（见「待确认」） |

## 决策

### D1 · provider 有序，不靠列表顺序

`ai_providers` 增 `priority int not null default 100`（迁移 V066）；数值小者优先，同值按 `created_at`。
管理员在 `/admin/ai` 能上下移动。**没有 priority 的顺序不算顺序**——靠 `created_at` 隐含排序，删一个加一个就会变。

### D2 · 触发条件是熔断打开，不是单份失败

沿用决策 013-D 已有的熔断（连续 5 份失败 → OPEN，5 分钟冷却 → 半开 1 份）。**熔断打开时**：

1. 按 priority 找下一个可用 provider（`enabled=true` 且未熔断）；
2. 更新 `ai_settings.active_provider_id`；
3. 写审计 `ai.provider.failover`（from / to / 原因 / 连续失败份数）；
4. 通知全部管理员与受影响教师（复用既有熔断通知通道，见 `docs/decisions/015` 与 T447 的 payload 渲染）；
5. 已 FAILED 的份按 013-D 的「恢复后重派一次」语义重派给新 provider。

单份调用失败**仍然只走 013-B 的重试**，不切 provider。

### D3 · 每份记录判分者

`submissions` 增 `graded_provider varchar(64)`（或等价列），在 AI 判分落库时写入 provider key。
复核台（`ReviewPage`）在该场发生过切换时显示「本场由 opencode-go 判 12 份、deepseek 判 28 份」。
**没有这个字段，跨模型混判就是不可审计的**——这也正是 013 当初反对的理由，把它补上才算解决了。

### D4 · 不静默：切换必须可见

- `/admin/ai` 顶部：当前 provider、是否发生过切换、切换时间与原因。
- 教师首页/批改总览：本场如果跨了 provider，显示一条中性提示（不阻断）。
- 本地模型作为最后一档时，额外标注「本地模型，判分质量未经 golden set 验证」（依据：2026-10-25 实测本地 qwen3.8-flash 同卷三次给 6/4/6，平均偏差 0.0 但最大偏差 4 分）。

### D5 · 不做的

- **逐份 fallback**：仍然不做（013 的理由成立）。
- **多 provider 并行判分比对**：不做，成本翻倍且没有评测基线支撑。
- **自动回切**：见待确认。

## 已确认（2026-10-25 用户拍板）

1. **自动回切**：主 provider 熔断恢复（半开探测成功）后**自动切回**主 provider（priority 最小的那条）。为避免抽插，回切前要求：主 provider 熔断关闭 + 备用 provider 已连续成功 ≥ 3 份 + 距上次切换 ≥ 10 分钟。回切同样写审计 `ai.provider.failback` 并通知管理员。
2. **切换粒度**：**只影响新派发**。已认领正在跑的份跑完（不中断在途调用），未认领的下一轮由新 provider 判。因此同一场作业可能跨 provider，靠 D3 的 `graded_provider` 让教师看见。

## 影响与代价

- 与 013-A 的冲突已在本文档显式记录：**013-A 作废，013 其余（B 重试、C 熔断恢复重派、D 熔断+通知、E 不做一键换模型）继续有效**。013 文档需在 A 行加一行指向本决策。
- 同一场作业的分数可能来自两个模型，口径差异**不会消失**，只能靠 D3 的字段让教师看见并复核。这是 1000 人规模下拿「可用性」换「口径绝对一致」的主动选择。
- 实现成本：1 个迁移 + 熔断钩子 + 审计 + 通知 + 一个 UI 标记，约 2–3 天（含测试）。
