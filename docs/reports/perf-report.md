# 性能实测报告（T122）

- 日期：2026-10-18
- 方法：`backend/scripts/perf_batch.py`，通过真实 HTTP API 走完整链路
  （建班 → 建作业 → 发布 → N 名学生提交 → 批量批改 → 轮询到完成）
- 环境：本机 macOS，PostgreSQL 16（Docker），后端 uvicorn 单进程

---

## 1. 编排开销（`AI_ENGINE=script_only`，无模型调用）

| 指标 | 数值 |
| :--- | :--- |
| 提交数 | 40 |
| 提交准备（40 次登录+加入+上传） | 0.7 s |
| 批改任务总耗时 | **0.3 s** |
| 每份 | **0.01 s** |
| 并发 | 3 |
| 尝试次数 | 中位数 1，最大 1 |

**说明**：`script_only` 不产生判定，因此 40 份全部落到 `skipped`（这是刻意设计——
降级引擎不伪造分数）。这个数字测的是**编排层本身**：任务创建、状态流转、
并发调度、SSE 事件、数据库写入。0.3 s / 40 份意味着编排不是瓶颈。

## 2. 真实模型延迟（`AI_ENGINE=dsh_headless`）

| 指标 | 数值 |
| :--- | :--- |
| 提交数 | 3 |
| 总耗时 | **7.4 s** |
| 每份（等效） | **2.47 s** |
| 全部完成 | 3 / 3 |
| 尝试次数 | 中位数 1，最大 1（**首次即通过校验**） |
| 并发 | 3 |

**并发有效性验证**：串行约需 3 × 6 s ≈ 18 s，实测 7.4 s，提速约 **2.5 倍**。
说明信号量并发调度确实生效，不是伪并发。

**外推**：40 份在并发 3 下约需 40 ÷ 3 × 7.4 ≈ **99 秒**（约 1.6 分钟）。
模型延迟是绝对瓶颈，编排开销可忽略。

## 3. 结论与阈值

| 项 | 结论 |
| :--- | :--- |
| 编排层 | 非瓶颈（0.01 s/份） |
| 模型层 | 瓶颈（约 6 s/份，随文本长度与 provider 波动） |
| 并发默认值 3 | 合理；提高到 6 理论再快约 1.7 倍，但会叠加 DSH 子进程与小模型限流风险 |
| 单份超时 | 180 s，远大于实测 6 s，留足余量 |
| 首次通过率 | 3/3 与 1/1 均一次通过，输出校验未触发重试 |

## 4. 未测的部分（诚实记录）

| 项 | 原因 |
| :--- | :--- |
| 40 份真实模型批改 | 需约 100 秒与 40 次模型调用，成本考虑只做了 3 份外推 |
| 多进程/多实例并发 | v1 单进程部署，SSE 事件总线为进程内实现，未测多实例 |
| 大文件（接近 100 MB）吞吐 | 只验证了上限拒绝逻辑（413），未测持续大文件压力 |
| OCR 并发 | 扫描件 OCR 为同步调用（约 5 s/页），未纳入并发压测 |

## 5. 复现方式

```bash
# 编排开销
AI_ENGINE=script_only uvicorn app.main:app --port 8010 &
python backend/scripts/perf_batch.py --count 40 --label orchestration

# 真实模型
uvicorn app.main:app --port 8010 &   # 默认 AI_ENGINE=dsh_headless
python backend/scripts/perf_batch.py --count 3 --label real-engine
```
