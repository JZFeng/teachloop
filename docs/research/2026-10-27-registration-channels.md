# 调研 — 注册与身份通道（邮箱 / 短信 / 微信）

- 日期：2026-10-27
- 上游：用户 2026-10-27 的要求（v1 用邮箱，手机与微信代码同批交付，全部可配置，微信是长期最重要通道）
- 下游：`specs/009-registration/spec.md`
- 结论速览：**同行几乎都走「验证码即身份」的通道抽象（一个 challenge/verify 流程，通道可插拔）**；把「注册」与「登录」当成两个流程的产品，最终都会合并回一个入口。

---

## 1. 为什么看别人

我们要做的不是「加一个注册页」，而是三条身份通道共用一套验证码生命周期与防刷策略。
如果只看自己要什么，很容易把「邮箱注册」写死成一个专用端点，等手机和微信进来时再拆一遍。
同行已经有成熟取舍，先看清楚再定结构。

---

## 2. 六个对照

### 2.1 Supabase Auth（开源自托管 + 托管，最贴近我们规模）

- **通道抽象**：`signInWithOtp` 一个方法吃邮箱或手机号，字段不同、流程相同；已存在则登录，不存在则建号，调用方不需要先问「注册还是登录」。
- **验证码生命周期**：OTP 有独立过期时间（默认 1 小时，可配），一次消费，校验失败计数可配。
- **频率限制**：按「每小时发送次数」分档配置，默认对同邮箱/同手机号限流；限流错误是独立错误码而不是笼统 429。
- **对我们有意义的取舍**：注册与登录合流后，前端只有一个「输入联系方式 → 输入验证码」的流程，与我们 `AC-3.4`（自助注册只能是学生）不冲突——角色由**建号那一刻**决定，不由端点决定。

### 2.2 Firebase Authentication

- **手机验证码是最强的一等公民**，邮箱走 magic link；两者共用 `verificationId` 这种一次性凭据。
- **防刷放在通道前面**：短信发送需要 reCAPTCHA / App Check 证明调用方是人，否则短信是纯成本攻击面（一条一毛，被刷就是真金白银）。
- **对我们有意义的取舍**：短信必须有**发送前的成本闸门**（人机校验或严格配额），不能只靠「每 IP 每分钟 N 次」。

### 2.3 Clerk

- 邮箱验证码 / magic link / OAuth 三条并列，**手机号验证码需要单独配置 provider**，属于可选通道而不是默认能力。
- 账号可以绑定多个身份（email + phone + 多个 OAuth），**身份与账号分离**：一个账号下挂多条 identity 记录，不是往账号表上加列。
- **对我们有意义的取舍**：这一条直接打中我们现有的 `users.wechat_openid` 单列设计——同一个用户在不同微信应用下 openid 不同，单列装不下第二个。

### 2.4 微信开放平台「网站应用」扫码 vs 公众号网页授权

| 项 | 开放平台网站应用扫码 | 公众号网页授权 |
| :--- | :--- | :--- |
| 入口 | PC 浏览器显示二维码，微信扫码确认 | 只在微信内置浏览器可用（`snsapi_base` / `snsapi_userinfo`） |
| 前置资质 | 开放平台开发者账号 + 网站应用审核，**需要已备案域名** | 已认证服务号 + 网页授权域名（同样要求备案） |
| 拿到的标识 | `openid`（按应用）+ `unionid`（同开放平台主体下统一） | `openid`（按公众号）+ `unionid`（绑定开放平台后） |
| 昵称头像 | 需另外的接口与用户授权 | `snsapi_userinfo` 可直接拉 |
| 我们的处境 | `teachloop.org` 走 Cloudflare Tunnel，**备案状态未确认**，未确认前不能承诺审核通过 | 同左，且 PC 用户完全无法使用 |

- **对我们的取舍**：两条都不是「今天申请明天能用」，且都卡在备案/主体资质上。
  代码可以先写完、配置可以先留空（未配置时通道不出现在登录页），这正好符合「代码先完成实现、凭证后补」。

### 2.5 阿里云短信服务（国内短信的默认选项）

- 发送前必须先过**签名审核**与**模板审核**，验证码模板另有变量格式要求；审核不是即时生效。
- 同一手机号、同一模板有服务商侧的流控（秒级、小时级、日级），我们自己还要再加一层，否则会撞到「触发流控但用户看不到原因」。
- 验证码通常 5 分钟内有效，超过要重新获取。
- **对我们的取舍**：短信通道的「未配置」不是一种异常，而是**默认状态**——所以我们不能把短信写进注册主流程，只能作为可选通道。

### 2.6 国内教育类平台（超星学习通 / 雨课堂 / 钉钉课堂）

- 学生侧主流是**手机号验证码**或**微信授权**，邮箱注册在 K12/高校场景里基本退居二线。
- 教师侧普遍保留「机构发码 / 管理员建号」，因为教师身份需要资质背书。
- **对我们的取舍**：与我们既有设计一致——自助注册只给 STUDENT（`AC-3.4`），教师继续走邀请码（`AC-3.2/3.3`）。这也解释了为什么「注册」不该顺手把教师角色放开。

## 3. 三条可复用的结论

1. **注册与登录合流**：一个 verify 端点，已存在则登录、不存在则建号，角色在建号时固定为 STUDENT。前端只有一条「联系方式 → 验证码」路径，换通道只是换输入框。
2. **身份与账号分离**：`user_identities` 表（账号 1 : N 身份），而不是继续往 `users` 上堆列。否则第二个微信应用、或「邮箱 + 微信」双绑，都会立刻卡住。
3. **通道配置是数据，不是代码**：发件人、SMTP/网关端点、短信服务商与模板、微信 appId/secret、限额与 TTL 全部可改；未配置的通道**不出现**在界面上，而不是出现后报错。

## 4. 我们与同行的差异（不照搬的部分）

| 点 | 同行做法 | 我们的选择 | 理由 |
| :--- | :--- | :--- | :--- |
| 人机校验 | reCAPTCHA / App Check | **不引入第三方人机校验**，v1 用严格配额 + 单目标冷却 | 学生群体在国内，reCAPTCHA 可用性差；短信通道开通时再评估 |
| magic link | 常见 | **不做**，只做验证码 | 邮件里的链接会被学校邮箱安全网关改写/预取，点击即消耗，故障难排查 |
| 密码 | 多数保留 | **自助注册不设密码**（passwordless），管理员密码登录保持现状 | 少一个「忘记密码」流程；管理员是既有例外，不动 |
| 微信主键 | 存 openid | **存 `unionid` 优先、`openid` 兜底** 的双键结构 | 同一个人换应用（公众号 ↔ 小程序）必须还是同一个人 |

## 5. 未确认事项（写进 spec 的假设清单，不要当事实用）

1. `teachloop.org` 的 ICP 备案状态 —— 决定微信「网站应用」与公众号网页授权能不能过审；**未确认前按「不可用」处理**。
2. 微信开放平台的账号主体（个人 / 企业）—— 个人主体通常无法申请网站应用扫码。
3. 短信服务商选型（阿里云 / 腾讯云 / 华为云）—— 影响签名与模板字段，不影响端口结构。
4. 个人邮箱的 SMTP 授权方式（QQ/163 授权码 vs 自建域名）—— 影响 `identity_channels.extra` 的必填字段，不影响表结构。
