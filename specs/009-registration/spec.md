## 1. 摘要

系统现在**没有注册**。账号只有四条来路：微信 code 自动建号、教师邀请码兑换、管理员 CLI/`/setup`、开发种子；其中微信的 `appId/secret` 在 `application.yml` 与 `application-prod.yml` 里一个字都没配，生产上 `/api/auth/wechat` 恒返回 503，前端也没有微信入口。

本规格把「获得一个账号」抽象成**通道无关的验证码流程**，但**注册与登录是两个独立行为**：

```
注册：填「名 / 姓」+ 邮箱 + 密码 → 建 PENDING 账号 → 发激活邮件
      → 点邮件里的链接 → 打开「确认激活」页 → 点按钮 → 账号 ACTIVE
      → 回登录页，用邮箱 + 密码登录
登录：邮箱 + 密码（直接登录）
      或 邮箱验证码（PENDING 与 DISABLED 一律拒绝）
```

**验证码只服务「忘记密码」与「验证码登录」，注册不再用验证码**（2026-10-27 用户提出，见 §9）。

两者共用同一套验证码服务与同一张 `verification_codes` 表，但**端点、失败语义、频控桶分开**。
任何一个入口都不允许在用户不知情的情况下建号。

三条通道同批交付，用配置开关控制谁对用户可见：

| 通道 | v1 默认 | 说明 |
| :--- | :--- | :--- |
| `email` | **开启** | 发件人暂时是个人邮箱，SMTP 或 HTTP 邮件网关两种驱动可切 |
| `sms` | 关闭（依赖资质） | 手机号验证码；服务商可插拔，未配置即不出现 |
| `wechat` | 关闭（依赖资质） | 开放平台扫码 + 公众号网页授权两种驱动；**长期主通道** |

### 1.1 关键设计立场

| 议题 | 立场 | 理由 |
| :--- | :--- | :--- |
| 注册与登录 | **两个行为、两组端点、两套失败语义**（`/register/*`、`/login/*`），底层共用验证码服务 | 登录时打错一个字母就会静默建出空账号，学生的作业全进错号；两者的采集字段、频控与文案本来就不同 |
| 注册碰到目标已存在 | PENDING → **重发激活邮件**（202，不建第二个账号）；ACTIVE → **409 `ALREADY_REGISTERED`** | 用户点了注册却没收到信是常态，重发比重建账号安全；已激活还来注册说明他以为没账号，直接引导去登录 |
| 登录碰到目标不存在 | 明确 **404 `NOT_REGISTERED`**，不发码 | 与上一条对称；绝不在登录流程里建号 |
| 角色 | 自助注册**只能** STUDENT；教师仍走邀请码 | 与 `AC-3.4`/`AC-3.5` 一致，禁止把学生提升为管理员 |
| 邮箱验证方式 | 注册用**激活链接**（点确认才生效），验证码只服务「验证码登录」与「忘记密码」 | 注册页已经收了密码，再让用户抄 6 位数字是流程代偿；链接的预取风险用「GET 只渲染确认页」化解 |
| 未激活的账号 | `status=PENDING`，**不能登录、不能访问任何接口** | 否则爬虫注册完就能调 AI，等于免费额度；PENDING 也让「重发激活邮件」有明确归属 |
| 密码 | 注册**必填**密码，**至少 8 位**；邮箱 + 密码可直接登录（2026-10-27 用户拍板改的，原先定的是 passwordless） | 用户要能「记住一个密码就进来」，不想每次都收邮件；代价是要多做一套忘记密码，见 US-77 |
| 密码登录的边界 | 生产环境**对所有 ACTIVE 账号开放**邮箱 + 密码登录 | 这会取代 2026-10-27 上午的测试账号白名单（`password_login_enabled`）；`ProdAuthTest` 里「教师密码登录 503」那条断言必须同步改掉，见 §7.3 |
| 身份归属 | 新增 `user_identities`（账号 1 : N 身份） | 现有 `users.wechat_openid` 单列装不下第二个微信应用；邮箱/手机/微信三条通道需要同一张表 |
| 微信主键 | `unionid` 优先，`openid` 兜底 | 换应用（公众号 ↔ 小程序）必须还是同一个人 |
| 配置位置 | `identity_channels` 表 + `SecretBox` 密文 | 复用 `ai_settings` 的既有先例；「以后换 Email Grid / 换短信服务商」不需要改代码 |
| 未配置的通道 | **不出现**在界面上 | 「出现了但一点就报错」是最差的用户可见状态 |
| 防刷 | 单目标冷却 + 分档配额，不引第三方人机校验 | 复用 `rate_limits` 表；reCAPTCHA 在国内可用性差，短信开通时再评估 |

| 自助换绑手机 | ✗ | 另立故事 |

## 3. 用户故事

### US-73 作为新学生，我注册后点邮件里的链接激活账号

我填名、姓、邮箱、密码，点注册；系统给邮箱发一封激活信。我点信里的链接，页面问我「确认激活这个账号吗」，我点确认，账号就活了，回到登录页用邮箱和密码进去。我要的不是抄一串数字来回切窗口。
**验收**：AC-73.1–73.13。

### US-74 作为没有邮箱习惯的学生，我用手机号验证码进入

学校发的账号信息只有手机号。手机通道开启时，我在同一个位置换成手机号，流程一模一样。
**验收**：AC-74.1–74.5。

### US-75 作为微信用户，我扫一下就进来（长期主通道）

中国人人手一个微信。我在 PC 上扫码、在微信里点授权，都应该是同一个账号；我之前用邮箱注册过，扫码后绑到同一个账号上，而不是凭空多出一个。
**验收**：AC-75.1–75.8。

### US-76 作为管理员，我改通道配置不用重启、也看不到密钥明文

发件邮箱从我的个人邮箱换成学校域名、或者以后接 Email Grid，我在设置页改完保存，下一次请求就生效；密钥只显示掩码。
**验收**：AC-76.1–76.5。

### US-77 作为学生，我忘记密码时能自己重设

注册要求设密码，就会有人忘。我不该为此给老师发消息等天亮——在登录页点「忘记密码」，填邮箱、收验证码、设新密码，就又能进了。重设成功后，别的设备上的登录应当一起失效。
**验收**：AC-77.1–77.5。

## 4. 验收标准

#### US-73 邮箱注册（激活链接）与登录

- [ ] AC-73.1 `GET /api/auth/channels` 是**公开**端点（未登录可访问），返回已启用通道：`email`、`sms`、`wechat` 各自的 `channel`、`label`、`targetHint`；未启用的通道**不出现**在数组里，登录页据此渲染 tab，不在前端硬编码
- [ ] AC-73.2 **注册提交** `POST /api/auth/register` 入参 `{channel, email, password, firstName, lastName}`：密码 ≥8 位、邮箱合法才受理；成功即建 **`status=PENDING`** 的 STUDENT 账号（`first_name` / `last_name` 落库，`display_name` 由二者按语言顺序合成）并发送激活邮件，返回 `202 { resendAfterSeconds }`，**此时不签发任何会话**
- [ ] AC-73.3 同一邮箱再次提交注册：账号是 **PENDING** → 重发激活邮件并返回 202（不报错、不建第二个账号）；账号是 **ACTIVE** → **409 `ALREADY_REGISTERED`**，不发信
- [ ] AC-73.4 **激活令牌**：32 字节随机、只存哈希、**24 小时**有效、**一次性消费**；`GET /api/auth/activate?token=…` **只渲染确认页、不激活**（对抗邮件网关的链接预取），`POST /api/auth/activate` 才把账号置为 ACTIVE
- [ ] AC-73.5 令牌无效 / 过期 / 已用 → 确认页给出对应文案（`TOKEN_EXPIRED` / `TOKEN_USED` / `TOKEN_INVALID`）并提供「重新发送激活邮件」，**不暴露该邮箱是否已注册**
- [ ] AC-73.6 **PENDING 与 DISABLED 账号不能登录、不能访问任何需要认证的接口**：密码登录返回 403 `ACCOUNT_PENDING`，验证码登录在发码阶段即 403，不签发会话
- [ ] AC-73.7 激活成功后返回登录页；用注册时的邮箱 + 密码可登录，`/api/auth/me` 返回 `role=STUDENT`
- [ ] AC-73.8 **姓名**：`first_name` / `last_name` 两个字段落库，`display_name` 自动合成为「姓 + 名」（zh-CN）或「名 + 姓」（en）；注册页的字段顺序随界面语言切换（中文「姓」在前，英文 First Name 在前），两栏都允许为空，为空时 `display_name` 取邮箱 `@` 前缀
- [ ] AC-73.9 请求体里出现 `role` 等提权字段一律忽略；注册只能得到 STUDENT，教师仍走 `AC-3.2/3.3` 的邀请码（承接 `AC-3.4`、`AC-3.5`）
- [ ] AC-73.10 频控（复用 `rate_limits`，注册、激活邮件重发、登录、验证码分桶计数）：同一邮箱重发激活邮件冷却 **60s**、1 小时 ≤**5** 次；同一来源 IP 1 小时 ≤**20** 次。超限 429 + `Retry-After`
- [ ] AC-73.11 **邮箱 + 密码登录**：`POST /api/auth/login` 对**任何 ACTIVE 且 `password_hash` 非空**的账号生效（不再限于 ADMIN 与白名单），密码错返回 401、PENDING/DISABLED 403；错误文案不区分「账号不存在」与「密码错误」
- [ ] AC-73.12 **邮箱验证码登录**（保留）：`POST /api/auth/login/challenge` 仅对已存在的 ACTIVE 账号发码，不存在 404 `NOT_REGISTERED`、PENDING 403；码分 6 位、10 分钟、错 5 次作废
- [ ] AC-73.13 `PUT /api/profile` 修改邮箱必须先过验证码（补掉现在「任何人都能把邮箱改成别人的」这个洞，见 `ProfileEndpoint.java:36-52`）

#### US-74 手机号验证码注册与登录

- [ ] AC-74.1 `identity_channels.sms.enabled=false`（默认）时，`/api/auth/channels` 不含 `sms`，登录页没有手机 tab；直接调用 challenge 返回 **404**（不存在的通道，而不是 403）
- [ ] AC-74.2 启用后**同样区分注册与登录两组入口**（`/api/auth/register/*`、`/api/auth/login/*`），行为与 `AC-73.2`–`AC-73.7` 对称；手机号先做规范化（中国大陆 11 位、可带 `+86`），非法格式在 challenge 阶段即拒绝
- [ ] AC-74.3 短信服务商未配置（签名/模板/密钥任一缺失）时，该通道视为**未启用**：不出现在通道列表，接口 404；不得返回 500
- [ ] AC-74.4 服务商发送失败（超时、5xx、余额不足）→ 返回 **502/503** 并带稳定错误码；该 `challengeId` 立即作废；用户 **30s** 后可重试；失败计入审计与指标，但不消耗该目标的「小时配额」
- [ ] AC-74.5 手机号唯一：同一号码已绑到其他账号时，注册入口返回 **409** 且**不透露**对方账号任何信息；已登录用户走绑定流程时可解绑后重新绑定

#### US-75 微信注册与登录

- [ ] AC-75.1 `identity_channels.wechat.driver` 支持 `wechat_web`（PC 二维码）与 `wechat_mp`（微信内网页授权），**两者可同时启用**；`/api/auth/channels` 对微信返回 `deepLink` / `qrTicket` 所需的元信息，前端据此决定渲染二维码还是跳转授权
- [ ] AC-75.2 授权入口 `POST /api/auth/wechat/authorize-url` 返回 `{url, state}`：`state` 一次性、**5 分钟**有效、绑定发起它的浏览器会话；回调 `state` 不匹配或过期返回 **400**，且不建号
- [ ] AC-75.3 code 换到 `{openid, unionid?}`；`unionid` 存在时以 `unionid` 作为身份主键，缺失时退化为 `(app_id, openid)`
- [ ] AC-75.4 同一 `unionid` 在 `wechat_web` 与 `wechat_mp` 两个应用下登录 → 命中**同一条** `user_identities` 记录、**同一个**账号（这是现有 `users.wechat_openid` 单列做不到的）
- [ ] AC-75.5 已登录用户完成微信授权 → **绑定**到当前账号，不新建；绑定后 `user_identities` 出现该身份，重复授权是幂等的（同身份二次绑定返回 200，不产生第二条记录）
- [ ] AC-75.6 微信 `appId/secret` 未配置时：通道不出现在列表，接口返回 **503** 与稳定错误码（保持现状「不伪造登录」），不得出现裸 500
- [ ] AC-75.7 迁移 `V0xx__identity_user_identities.sql` 把 `users.wechat_openid` 的非空行回填为 `user_identities(channel='wechat', external_id=openid, external_app='legacy')`；回填后可查询到原账号。旧列保留一个版本周期，期间**只读不写**
- [ ] AC-75.8 微信首次建号仍是 `STUDENT`、`displayName` 占位「微信用户」、`email` 为空（现有行为不变）；不允许微信通道顺手把账号设成 TEACHER/ADMIN

#### US-76 通道配置

- [ ] AC-76.1 `GET /api/admin/identity-channels`（仅 ADMIN，非 ADMIN 一律 **403**）逐通道返回：`enabled`、`driver`、发件人 / 端点、配额、TTL、`hasSecret`（布尔）与密钥掩码（形如 `sk-****1234`），**任何情况下不返回明文密钥**
- [ ] AC-76.2 `PUT /api/admin/identity-channels/{channel}` 保存后**下一次请求即生效**，无需重启进程（与 AI 设置「保存后重启生效」不同，本规格明确要求即时）
- [ ] AC-76.3 关闭通道时，该通道所有未消费的 challenge 立即失效（verify 返回 400「通道已关闭」），已登录用户不受影响
- [ ] AC-76.4 密钥用 `SecretBox`（AES-GCM）加密入库；`TEACHLOOP_SECURITY_SECRET` 变更导致解密失败时，该通道标记为 `secretUnreadable=true` 并**按未启用处理**，不得抛堆栈给用户
- [ ] AC-76.5 每次配置变更写审计事件（操作者、通道、变更字段名），**不记录密钥值**；审计可用 `AuditPort` 查询到

#### US-77 忘记密码

- [ ] AC-77.1 `POST /api/auth/password-reset/challenge` 入参 `{channel, email}`：账号**存在**时发验证码；账号**不存在**时返回 **404 `NOT_REGISTERED`**、不发码（与登录入口同一套语义）
- [ ] AC-77.2 `POST /api/auth/password-reset/verify` 入参 `{challengeId, code, newPassword}`：验证码正确且新密码 ≥8 位时更新 `password_hash`，返回 200；账号直接**不自动登录**，要求用新密码走一次登录（避免「改密即接管会话」）
- [ ] AC-77.3 重设成功后把 `users.session_invalid_before` 置为 now()：**该账号所有已有会话立即 401**（复用 2026-10-27 改密码那条机制）
- [ ] AC-77.4 复用同一套验证码表与频控桶（与注册/登录分开计数）；验证码 6 位、10 分钟、错 5 次作废
- [ ] AC-77.5 重置过程中**不透露**原密码、不返回账号的任何资料；仅 `email` 通道可用时该入口才出现（`sms` 通道将来复用同一端点）

## 6. 失败路径

| 场景 | 行为 |
| :--- | :--- |
| 通道未启用 | 404（视为不存在）；界面不出现该 tab |
| 通道启用但服务商未配置 | 同上，404；日志 warn 一次，不刷屏 |
| **注册**时目标已存在 | 409 `ALREADY_REGISTERED`，**不发码**；前端给「去登录」按钮 |
| **登录**时目标不存在 | 404 `NOT_REGISTERED`，**不发码**；前端给「去注册」按钮 |
| 注册与登录之间来回跳 | 邮箱/手机原样带到另一个页面，不用重填 |
| 发码超频 | 429 + `Retry-After`，文案给剩余秒数 |
| 验证码过期 | 400，错误码 `CODE_EXPIRED`，引导重新获取 |
| 验证码错误 | 400，错误码 `CODE_INVALID`，不回显剩余次数 |
| 验证码错误 5 次 | 400，错误码 `CODE_ATTEMPTS_EXCEEDED`，该 challenge 作废 |
| 邮件/短信服务商 5xx | 502/503，challenge 作废，30s 后可重试，不扣小时配额 |
| 微信 state 过期/不匹配 | 400，不建号 |
| 微信 appId/secret 缺失 | 503，稳定错误码 |
| 密钥解密失败 | 通道按未启用处理，`secretUnreadable=true`，不抛堆栈 |
| 手机号已被占用 | 409，不透露对方信息 |
| 并发重复 verify 同一 challenge | 只有一个成功（`consumed_at` 条件更新），另一个返回 400 `CODE_USED` |
